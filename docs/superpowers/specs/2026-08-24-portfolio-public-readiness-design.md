# 个人作品网站公开发布就绪设计

## 背景

现有网站已经具备暖米色、咖啡色的编辑式视觉语言，以及首页、工作流、视觉作品、项目详情、思考文章、灯箱、移动端布局和批量视觉清单。第三阶段不重新设计网站，而是把它从“本地可演示的作品集框架”补成“技术上可公开发布、内容上容易替换、不会伪造个人事实的简历网站”。

当前真实姓名、邮箱、微信二维码、正式工作流截图和约 60 张作品尚未提供。系统必须允许这些字段为空，并隐藏对应入口；公开发布校验会明确指出缺少哪些真实内容，但不会生成虚假姓名、成绩、联系方式或项目数据。

## 方案选择

### 方案 A：只修部署阻断

修复 GitHub Pages 子路径、canonical 和素材校验，改动最少，但首页仍不能充分表达经历、案例与联系闭环。

### 方案 B：发布就绪与内容就绪双轨（采用）

在修复部署阻断的同时，完善简历信息呈现、案例关联、内容预检、社交分享、键盘操作和填写模板。所有增强继续使用 Astro 内容集合与静态生成，不引入后台和数据库。

### 方案 C：引入 CMS、表单与图像服务

编辑体验更像商业网站，但需要账号、外部服务、持续费用和更多安全维护。对当前个人作品网站属于过度建设，因此不采用。

## 目标与验收标准

1. 网站在根路径和 GitHub Pages 项目子路径下，内部链接、图片、canonical、Open Graph 和 sitemap 均正确。
2. 每个可分享页面都有稳定的默认分享图；文章与案例可以覆盖为自己的图片。
3. 首页在不改变主视觉的前提下，显示已有经历数据和清晰的作品/工作流入口；个人信息为空时不出现假内容。
4. 视觉作品可以区分 AI 前、AI 辅助与混合制作，并可关联项目或工作流产出。
5. 移动导航关闭时不能聚焦屏幕外链接，打开后可用键盘完整操作；灯箱切换会通知读屏软件。
6. Windows 换行不会让素材校验误报；内容引用、图片路径和发布必填项可以在部署前自动检查。
7. 一条 `npm run validate` 命令完成日常质量检查；一条严格命令明确判断是否满足公开发布条件。
8. 生产构建、桌面与移动端测试、子路径构建测试和本地视觉复查全部通过。

## 信息架构与页面设计

### 首页

保留现有超大英文标题、节点画布和非对称排版。首屏增加两条克制的文字入口：“查看工作流”和“浏览视觉作品”，不增加销售式大按钮。年份改为自动读取当前年份。

关于区继续放在首页，不新建 About 页面。它会使用 `profile.experience` 渲染一条紧凑的经历时间线；可选的所在地、合作状态与简历 PDF 只有在填写后才显示。工具标签继续保留。

### 视觉作品

视觉记录增加：

- `era`: `pre-ai`、`ai-assisted` 或 `hybrid`
- `description`: 一句使用场景或任务说明
- `tools`: 可选工具列表
- `workflowId`: 可选工作流关联

分类筛选仍按内容类别生成，另增加一个轻量的“创作阶段”筛选。卡片保持简洁；年代、说明和工具主要在灯箱中呈现。项目和工作流关联各自使用独立文字链接，不让整张卡片承担两个导航行为。

### 项目与工作流详情

项目图集条目允许可选 `caption`，用于解释过程图。工作流详情在存在关联视觉作品时，显示“这个流程产出的作品”区域。项目和工作流正文仍使用 Markdown，避免为了结构化而增加难维护的字段。

### 思考与演示内容

内容模型增加 `demo` 布尔值。开发预览可以显示演示内容并带轻量“结构示例”标识；严格公开发布校验会拒绝任何仍为 `demo: true` 的记录。这样本地预览保持完整，同时公开发布不会把“等待替换”误当真实成果。

## URL、部署与资源架构

建立唯一的 URL 工具：

- `joinBase(base, path)` 负责将任意站内路径与 Astro `BASE_URL` 安全拼接。
- `withBase(path)` 供 Astro 页面和组件使用。
- 完整外部 URL、`mailto:`、锚点和数据 URL 原样返回。

导航、详情链接、图片、二维码、灯箱数据和社交图片全部经过同一工具。Astro 的项目仓库 `base` 始终带尾斜杠。

GitHub Actions 使用仓库变量 `SITE_URL`；未设置时根据仓库所有者生成 `https://<owner>.github.io`。页面路径仍由 `base` 添加。生产构建不得再生成指向 localhost 的 canonical 或 sitemap。

## SEO 与分享设计

`BaseLayout` 扩展以下能力：

- 默认 1200×630 分享图片及图片替代文本
- `og:site_name`、`og:locale`、Twitter/X large image card
- `website` 与 `article` 类型
- 可选发布日期
- 可选 `noindex`
- 可选 JSON-LD

404 输出 `noindex,follow`。`robots.txt` 由 Astro 静态端点根据站点 URL 与 base 生成。首页只输出不依赖虚假身份的 `WebSite` 结构化数据；填写真实姓名后才允许输出 `Person` 数据。文章输出 `Article` 数据，项目输出 `CreativeWork` 数据，字段仅来自已有内容。

## 辅助访问与交互

移动导航按钮通过 `aria-controls` 关联导航。移动导航关闭时设置 `inert` 与 `aria-hidden`；打开时聚焦第一条导航，Tab 在菜单和关闭按钮之间循环，Escape 或关闭后焦点返回菜单按钮。桌面断点会移除移动状态，避免导航不可访问。

当前栏目使用 `aria-current="page"` 和细下划线提示。灯箱标题区域使用 `aria-live="polite"`，切图后播报新作品。交互仍尊重 `prefers-reduced-motion`。

## 内容校验与素材流程

视觉导入比较内容前统一 LF/CRLF；仓库用 `.gitattributes` 固定自动生成 YAML 的换行。导入清单继续作为唯一数据源，并验证：

- ID 唯一且引用的 `projectId`、`workflowId` 存在
- `versionOf` 指向现有视觉记录
- 所有内容封面、图集、二维码和视觉图片实际存在于 `public/images`
- 声明宽高与图片实际宽高一致
- 图片长边和文件大小超过建议值时给出明确警告
- profile 内容集合恰好一个文件

`npm run content:preflight` 执行结构与文件检查；`npm run content:release` 额外要求至少一个非演示工作流、一个非演示项目、六张非演示视觉作品，以及可用的邮箱或微信二维码。严格校验不混入普通本地构建。

删除视觉清单记录后，生成器支持受限的 `--prune`：只删除 `src/data/visuals/generated/` 中不再对应清单的 YAML，并在操作前输出具体文件；不会触碰其他目录或手写内容。

## 测试设计

单元测试覆盖：

- 根路径与 `/repo/` 基路径拼接
- 外部 URL、锚点和 mailto 不被改写
- CRLF 与 LF 生成内容等价
- 新视觉字段、交叉引用与安全清理列表
- 内容预检的缺图、错误引用与严格发布模式

Playwright 覆盖：

- 默认和详情页 SEO 元数据
- 404 noindex 与 robots 内容
- 移动菜单的 inert、焦点进入、Tab 循环、Escape 恢复
- 灯箱 `aria-live`
- 首页 CTA 与经历时间线
- 代表页面内所有站内链接和图片返回成功状态

另执行一次设置 `GITHUB_REPOSITORY=owner/portfolio`、`GITHUB_ACTIONS=true` 和生产 `SITE_URL` 的构建，检查生成 HTML、sitemap 和资源路径包含 `/portfolio/` 且不含 localhost。

## 文档与维护

新增三份内容文档：

1. 个人资料与上线清单：姓名、联系方式、社交账号、简历 PDF、分享图。
2. 工作流案例模板：问题、输入输出、关键步骤、本人判断、使用频率、真实产物。
3. 项目案例模板：背景、限制、判断、过程、结果和复盘。

README 说明本地预览、日常校验、严格发布校验、子路径预览和演示内容规则。

## 明确不做

- 不伪造姓名、客户、项目成绩、节省比例或联系方式。
- 不增加 CMS、登录、数据库、联系表单或外部分析服务。
- 不替用户公开发布、创建 GitHub 仓库或推送远程。
- 不在缺少真实图片时生成冒充真实项目的作品。
- 不推翻已经确认的米色、咖啡色编辑式视觉方向。
